# business-message の背景と設計

この文書は開発・保守用であり、メッセージ作成時の追加指示ではない。
個々のメッセージの目的・検討結果は、その原本Markdownの「作成者向け情報」に保存する。

## 背景と目的

文章を整える前に、作成者が相手に何を伝え、何を判断・実行してほしいかを確認する。
AIは矛盾や理由の不足を指摘し、必要なら結論の変更を提案する。
ただし、分類と完成の判断はユーザーが確定し、AIが未承認の内容を受け手向け本文に加えない。

完成物は、受け手が最初に要点を読め、必要な場合だけ詳しい背景を開くWebページ型のHTMLとする。
再編集できるMarkdownには本文だけでなく、作成者の目的と重要な検討結果も残す。
その非公開情報は、共有するHTMLのソースにも含めない。

## 採用した設計と理由

| 決定 | 理由 |
|---|---|
| 主張・提案・相談・質問・依頼・報告・通知・注意喚起から、1ファイルにつき1分類 | 作成者がそのメッセージの趣旨を一つに定められるようにする。独立した趣旨は別ファイルにし、従属する承認依頼などは分割しない。 |
| AIが分類を理由付きで提案し、ユーザーが確定する | AIが作成者の意図を誤解したまま本文を作ることを避ける。 |
| AIが完成を提案し、未解決事項と影響を示してユーザーが最終承認する | 完成の可否を作成者が判断できるようにする。 |
| 受け手と、実現したい状況を確認し、原則1ターン1問で聞く | 誰に何をしてほしいかを確認する。細部を一度に聞く負担を増やさない。 |
| 事実・推測・意見を区別し、内容を批判的に検討する | 理由の不足や反論を見落としたまま文章だけを整えることを避ける。 |
| 公開本文にはユーザーが明示・承認した内容だけを含める | 調査結果やAIの推測を、作成者の主張として勝手に追加しない。 |
| Markdownを原本とし、メッセージ・背景情報・作成者向け情報の順で保存する | 再編集に必要な情報を残し、共有する内容と非公開情報を区別する。 |
| HTMLは要点を常時表示し、追加の背景は開閉できる形にする | 最初に必要な内容を読み、詳しい根拠は必要な人だけが読めるようにする。重要な判断材料は背景欄に隠さない。 |
| 表・Mermaidを優先し、必要な複雑な図や画像だけ `visual` フェンスで指定する | Markdownで表現できる内容は機械変換し、AIによる素材生成が必要な範囲だけを残す。 |
| AIが図表の種類・位置・内容を決め、文章の完成案と一緒に承認を得る | 個別の図表ごとに確認を繰り返さず、本文と図の内容を一度に確認できるようにする。 |
| 文章のHTML変換と図表素材の生成を分ける | HTML全体をAIに書き直させず、承認済み本文を保つ。 |
| CSSと画像を単一HTMLに埋め込む | HTMLと素材を別々に受け渡す必要をなくす。 |

## 現在の設計と比較できる代替案

保守時に設計を見直すための比較資料とする。

| 代替案 | 現在の設計との違い・変更時に判断すること |
|---|---|
| 1メッセージに複数の分類を付ける | 趣旨を一つに定める方針を変更する。独立した趣旨を分割する基準も変更する必要がある。 |
| 分類や完成をAIだけで確定する | 現在のユーザー承認を省く。作成者が意図の誤解を訂正する機会をどこに設けるかを決める必要がある。 |
| 図表を一つずつ承認する | 完成案での一括承認を変更する。確認回数が増えるため、ユーザーの希望を確認する必要がある。 |
| HTML全体をAIで生成し直す | 本文と図表素材を別々に扱う方式を変更する。承認済みの文章が変わっていないことを確認する方法が必要になる。 |
| HTMLだけを保存する | 作成者の目的・重要な検討結果をどこに残すか、HTMLを再編集する方法を決める必要がある。 |
| 設計文書を毎回読み込む | 通常の利用にも開発用の説明を読み込むため、コンテキスト消費が増える。現在は変更時・必要な不具合調査時だけ読む。 |

## 実装と検証

変換は `scripts/render.js` が行う。Node.jsの依存関係は `package.json` と `package-lock.json` に記録し、`npm ci` で導入する。Pythonは必要としない。
対応環境はLinux・macOSとNode.js 22（Maintenance LTS）・24（Active LTS）。Node.js標準APIとES Modulesを使い、ネイティブアドオンやUnix専用シェルを必要としない依存関係を選ぶ。CIは両OSと両Node.jsバージョンの4構成で実行する。LTSの切り替わり時には `engines` とCIの対象を更新し、テストが通ってから対応を宣言する。
公式リリース予定: https://github.com/nodejs/Release/blob/main/schedule.json

Mermaidには別途 `mmdc` が必要であり、存在しない場合はエラーにする。ローカルnpmパッケージのJavaScriptのCLI入口をNode.jsで直接実行し、PATH上の `mmdc` も利用できる。

- `--stage`：文章と表をHTMLへ変換し、MermaidをSVG画像へ変換する。`visual` は専用マークのまま残す。
- 図表素材の生成：承認された指示だけを使い、原本と同じディレクトリの `assets` に保存する。
- `--final`：素材の存在とSVGの許可要素・属性を確認し、画像を埋め込む。未解決の専用マークを残さない。
- 通常のMarkdown画像も同じディレクトリ以下の対応形式だけを埋め込む。外部URLや見つからない画像はエラーにする。画像の実パスを原本ディレクトリ内に限定し、シンボリックリンクによる逸脱も拒否する。
- 作成者向け情報は変換対象から除外する。コードブロック内の見出しで公開・非公開の区切りを変更しない。

スキルのディレクトリで `npm test` を実行する。Node.js標準テストランナーによる19件のテストで、次の内容を確認する。

- 公開本文・表の出力と、非公開情報の不掲載。
- `--stage` と `--final` による使用例のHTML生成。
- 分類・セクション順序・必須見出し・`visual` の一意性。
- 画像の埋め込み、不正なSVGや外部画像の拒否、素材不足・重複時の失敗。
- Mermaid CLIの呼び出しと出力埋め込みを模擬したテスト、CLI不在時のエラー。
- Mermaidを含まない原本・素材からの再変換が同一のHTMLになること。
- CRLF、空白・日本語を含むパス、CLIの失敗、XMLの不正な構造。

## 未検証・未決定事項

- 実際の `mmdc` とブラウザーを使うMermaid生成は未検証。模擬テストの成功とは区別する。
- Mermaidを含む出力が同一バイト列になることは保証しない。CLI・ブラウザー・フォント環境に依存する。
- 聞き取り、分類提案、批判的検討、承認待ちを、エージェントが実際の対話で守るかは自動テストで検証していない。
- AIが作る図の文字・数値・関係の正しさは、変換プログラムでは判断しない。原本と比較して確認する。

## 資料の保守方針

この文書には現在の仕様・設計理由・比較案・検証範囲を記載し、変更時には該当箇所を更新する。日付付きの変更ログや移行履歴は追記しない。
期待する動作は `SKILL.md` に記載し、プログラムで確認できるものはテストにも反映する。
変更履歴と、その変更で実行した検証結果はコミットまたはPRに記載する。
