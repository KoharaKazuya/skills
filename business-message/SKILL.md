# ビジネスメッセージを作る

## 基本ルール

- 分類は **主張、提案、相談、質問、依頼、報告、通知、注意喚起** の8種類から1ファイルにつき一つ。AIが理由付きで提案し、**ユーザーの確定を待つ**。承認依頼など従属する要素は別ファイルにしない。独立した趣旨が混在したらMarkdown/HTMLを分割する。
- **このメッセージを通じて相手や状況がどうなってほしいか**を必ず聞き取る。これは作成者だけの情報であり、公開する必要はない。
- 受け手、伝えたいこと、求める判断や行動、必要な背景を聞く。質問は原則1ターン1問。答えが結論を変える重要な疑問から聞き、細部の網羅を目指さない。
- 事実・推測・意見を分け、矛盾、理由の不足、相手の反論、理解に必要な情報の欠落を**主体的に指摘**。必要なら主張・結論自体の変更を提案する。無理に反対意見を作らない。
- 相手が話題・結論・求められる判断や回答を理解でき、重要な問題をユーザーに伝えたら、AIが完成を提案する。未解決事項とその影響を明記し、**ユーザーが最終承認**するまで完成としない。
- 受け手に見せる本文・根拠・図表にはユーザーが明示・承認した内容だけを含める。AIが推測した原因、未承認の提案、外部で発見した事実は勝手に含めない。事実が不明なら不明と書く。
- 普通の平易な日本語を使用し、主語と動作を具体化。意味を変える省略・難しい熟語・不要な修辞を避ける。

## 原本の構造

1件につき `message.md` を原本として保存する。前置きYAMLの `type` は上記8分類のうち1つ、`title` は文字列。

- `# メッセージ`：受け手に常時見せる要点・依頼・必要な判断材料。短く開始するが必要な量だけ書く。
- `# 背景情報`：受け手が必要に応じて開く追加の根拠・出典・詳細。重要な判断材料をここに隠さない。
- `# 作成者向け情報`：公開不可。`## 実現したい状況` と `## 重要な検討結果` を持つ。採用・却下した重要な案と理由を短く保存。全会話の記録は保存しない。

生成プログラムは `# 作成者向け情報` をHTMLに含めず、ソースにも残さない。原本Markdownは非公開情報を含むため共有しない。
上記3セクションはこの順序で置く。コードブロック内の見出しはセクションの区切りとして扱わない。
通常のMarkdown画像も原本と同じディレクトリ以下に保存する。SVG・PNG・JPG・WebPをHTMLに埋め込み、外部画像URL・親ディレクトリの画像・存在しない画像はエラーにする。

## 図表選択と承認

- 比較や一覧はMarkdown表、流れや関係は `mermaid` フェンスを優先する。文章のみで伝わるなら図表を増やさない。
- MarkdownとMermaidで表現できない複雑な図、イラスト、画像のみ `visual` フェンスで指定する。例：

~~~visual
id: architecture-comparison
type: diagram
instruction: |
  承認された構造だけを左右で比較する。本文にない要素を加えない。
~~~

- `id` は英数字・ハイフンのみの一意な名前。`type` は `diagram`、`illustration`、`image`。指示は**具体的かつ承認内容に限定**する。
- 図表の種類・位置・内容はAIが決め、文章の完成案と同時に見せて**ユーザーから一括承認**を得る。図表によって結論や根拠を変えない。

## HTMLへの2段階変換

1. `node scripts/render.js path/to/message.md --stage`。文章・表を機械変換し、MermaidはCLIでSVGへ変換する。`visual` はHTMLの専用マークとして**残す**。
2. HTMLに残った `data-visual-id` ごとに、承認済み指示に従いLLM（あるいは画像生成手段）で**その図表素材だけ**作る。HTML全体をLLMに渡して書き直させない。素材はMarkdownと同じディレクトリの `assets/<id>.svg` / `.png` / `.jpg` / `.webp` に保存。生成画像の説明もMarkdownで確定済みの内容だけにする。
3. 静的なSVG以外（script、イベント属性、foreignObject、外部URL等）は使用しない。生成した図の数値・文字・関係が原本と一致するか点検し、必要なら再生成する。
4. `node scripts/render.js path/to/message.md --final`。専用マークを素材に**機械的に置換**して単一のHTMLへ埋め込む。素材がない、無効、安全に埋め込めない場合は失敗とし、完成とは報告しない。
5. スキルのディレクトリで `npm test` を実行する。完成物で本文不変、非公開情報の不掲載、全マークの消失を確認する。Mermaidを含まない場合、生成済み原本と素材が同一なら再変換結果も同一。Mermaidの出力はCLI・ブラウザー・フォント環境に依存するため、同一バイト列になるとは断定しない。

実行環境: Node.jsのサポート中のLTSを対象とする。2026-10-12時点ではActive LTSの24とMaintenance LTSの22に対応する。Pythonは不要。Linux・macOS・Windowsで同じNode.jsコマンドを使う。スキルのディレクトリで `npm ci` を実行してから変換する。依存関係は `package.json` と `package-lock.json` で管理し、テストはNode.js標準のテストランナーを使う。LTSの切り替わり時には `engines` とCIの対象を更新し、新しいバージョンのテストが通ってから対応を宣言する。

Mermaidを使う場合だけ、スキルのディレクトリで `npm install --no-save --package-lock=false @mermaid-js/mermaid-cli` を追加実行する。ローカルのCLIをNode.jsから直接起動するため、Windowsでもシェルのコマンド解釈に依存しない。Linux・macOSではPATH上の `mmdc` も利用できる。CLIに必要なブラウザー・OS依存ライブラリ・日本語フォントは各環境で用意し、実際の原本の変換で確認する。CLIがない、起動に失敗した、素材が生成されなかった場合は成功扱いせずエラーにする。通常の `npm test` はCLI連携を模擬して検証し、実ブラウザーでの生成成功は意味しない。HTMLはCSSと画像を埋め込む一つのファイルにする。

## 開発・保守時だけ読む文書

通常のメッセージ作成・推敲・HTML生成では、[背景と設計](references/design.md)を読まない。
次の場合だけ、変更や調査を始める前に読む。

- このスキルのルール、Markdown形式、変換プログラムを変更する。
- 不具合を調査しており、このファイル・コード・テストだけでは期待する動作がわからない。
